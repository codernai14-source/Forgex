# 登录租户选择交互码设计

## 背景与根因

当前登录接口只完成账号、密码和验证码校验并返回租户列表。租户选择接口随后仅依据请求体中的 `account` 和 `tenantId` 查询绑定关系，查询成功后直接创建 Sa-Token 会话。攻击者不需要证明自己刚刚完成过该账号的登录校验，就能调用租户选择接口建立会话。

## 目标

- 首次选择租户必须证明调用方刚刚完成该账号的登录校验。
- 证明材料短期有效、不可猜测、绑定账号和登录终端，并且只能成功消费一次。
- 已登录用户正常切换租户时继续依赖现有 Sa-Token 会话，不要求重新输入密码。
- Web 与 Android 客户端使用相同契约。

## API 契约

`POST /auth/login` 成功响应的 `data` 从租户数组调整为：

```json
{
  "interactionCode": "opaque-random-code",
  "tenants": []
}
```

`POST /auth/chooseTenant` 和兼容别名 `POST /auth/choose-tenant` 的请求新增可选字段：

```json
{
  "loginTerminal": "B",
  "tenantId": "1",
  "account": "demo",
  "interactionCode": "opaque-random-code"
}
```

字段在 Java DTO 中可空，是为了允许已登录会话切换租户；首次建立会话时必须提供。

## 后端设计

登录校验成功后生成随机 UUID 交互码。Redis 键使用交互码 SHA-256 摘要，避免明文交互码出现在 Redis 键列表中；值保存用户 ID、账号和规范化后的登录终端，TTL 固定为 5 分钟。

首次选择租户时按以下顺序处理：

1. 校验账号、租户和用户租户绑定关系。
2. 判断当前是否存在账号一致的有效 Sa-Token 会话。
3. 不存在有效会话时，校验交互码对应的用户 ID、账号和终端。
4. 使用 Redis 原子比较并删除操作消费交互码，保证并发请求最多一个成功。
5. 只有消费成功后才能调用 `StpUtil.login` 建立正式会话。

若已有有效会话，只有会话登录 ID 与请求账号一致时才允许切换租户。不能使用账号 A 的会话切换账号 B 的租户。

交互码缺失、错误、过期、上下文不匹配或已消费时统一返回状态码 `602`，提示登录验证已过期，请重新登录。统一错误避免泄露交互码是否存在。

## 客户端设计

Web 登录页和 Android 登录状态在登录成功后仅将交互码保存在内存中，并在首次选择租户时回传。选择成功或失败后清除交互码；交互码错误或过期时回到登录步骤，要求重新完成登录。

Web 主布局中的已登录租户切换不传交互码，依赖当前 Cookie/Sa-Token 会话。HTTP 响应拦截器不再通过仅有的 `account + tenantId` 自动恢复认证；会话失效时跳转重新登录。

Android 当前只实现首次登录后的租户选择，因此仓库接口、请求模型和 ViewModel 状态同步携带交互码。

## 安全与异常边界

- 原始交互码仅返回客户端一次，不写业务日志。
- Redis 不可用时登录不能发放无状态替代凭证，接口按现有异常链路失败。
- 校验绑定关系前不消费交互码，避免无效租户输入使合法登录挑战失效。
- 身份匹配后采用原子消费，防止并发重放。
- 新一次登录可以产生新的独立交互码；每个交互码各自只允许消费一次并在 5 分钟后自动失效。

## 测试与验证

- 单元测试覆盖交互码创建、身份/终端绑定、过期或不存在、一次性原子消费。
- 后端回归测试覆盖首次选择缺少交互码被拒绝、合法交互码成功、已登录同账号可切租户、已登录账号不匹配被拒绝。
- Web 执行 TypeScript/Vite 构建，确认新响应和请求类型闭合。
- Android 编译 `core:network` 与 `feature:auth`，确认 Retrofit 模型和状态流闭合。
- 后端执行 Auth 模块测试及编译。
