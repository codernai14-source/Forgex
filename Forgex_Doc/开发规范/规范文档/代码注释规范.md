# 代码注释规范

> 分类：开发规范 / 规范文档
> 版本：V0.8.0

本规范约束 Forgex 三端（后端 Java / 前端 TypeScript+Vue / 安卓 Kotlin）的代码注释要求，明确「什么必须写、什么不该写」，确保注释有价值、与代码一致、不成为维护负担。

---

## 一、注释原则

### 1.1 核心原则

| 原则 | 说明 |
|---|---|
| 注释解释「为什么」，不解释「是什么」 | 代码本身已说明做了什么，注释应补充意图、背景、约束 |
| 注释与代码同步 | 改代码必改注释，过时注释比没注释更危险 |
| 公开 API 必须有文档注释 | 类、方法、参数的契约靠注释传达，不靠读实现 |
| 避免冗余注释 | 显而易见的代码不加注释，如 `i++; // i 加 1` |

### 1.2 业务注释与实现说明的边界

| 必须写 | 不该写 |
|---|---|
| 业务规则与领域约束（如「主密钥必须 32 字节」） | 代码字面含义（如 `// 设置状态为 ACTIVE`） |
| 非显然的设计决策与权衡（如「用 GCM 而非 CBC，因需认证标签」） | 能从类型签名推断的信息 |
| 外部依赖的隐含约定（如「该接口要求幂等」） | 第三方库的用法说明（交给官方文档） |
| 临时绕过问题的原因与关联 issue | 历史变更记录（交给 Git） |
| 安全相关限制（如「禁止在此方法记录明文密钥」） | 个人风格注释（如「我觉得这样更优雅」） |

## 二、Java 注释规范（Javadoc）

### 2.1 类注释

所有公开类（public class）必须有 Javadoc，说明职责与用途：

```java
/**
 * 密钥管理服务实现（KMS）。
 * <p>
 * 使用主密钥（Master Key）对所有业务密钥进行 AES-256-GCM 加密后存储到数据库。
 * 主密钥从外部环境变量或密钥文件注入，不落库。
 * <p>
 * 所有密钥操作均记录到审计日志表 {@code sys_kms_key_log}。
 *
 * @author Forgex Team
 * @version 1.0.0
 * @see KmsService
 */
@Service
public class KmsServiceImpl implements KmsService {
```

规范要点：
- 首行是一句话概述（句号结尾），后续段落用 `<p>` 分隔。
- `@author` 必填，`@version` 标注当前版本。
- `@see` 引用关联类，`{@code}` 标注代码字面量。

### 2.2 方法注释

公开方法必须有 Javadoc，包含参数、返回值、异常：

```java
/**
 * 获取当前激活的密钥明文。
 * <p>
 * 按 alias 查找状态为 ACTIVE 且版本号最大的密钥，解密后返回。
 *
 * @param alias 密钥别名（业务唯一标识）
 * @return 密钥明文（Base64 编码），如无激活密钥返回 null
 * @throws IllegalStateException 密钥检索或解密失败时抛出
 */
@Override
public String getActiveKey(String alias) {
```

规范要点：
- `@param` 每个参数一行，说明参数含义与约束。
- `@return` 说明返回值含义，void 方法省略。
- `@throws` 列出可能抛出的业务异常及触发条件。
- 私有方法如逻辑复杂也应加注释，简单私有方法可省略。

### 2.3 字段注释

公开常量与配置字段必须有注释：

```java
/** 主密钥长度（字节），AES-256 需要 32 字节 */
private static final int MASTER_KEY_SIZE = 32;
```

### 2.4 行内注释

仅在逻辑非显然时添加，说明意图而非操作：

```java
// GCM 模式 IV 每次随机生成，无需复用，12 字节为 NIST 推荐长度
byte[] iv = new byte[GCM_IV_LENGTH];
new SecureRandom().nextBytes(iv);
```

## 三、TypeScript / Vue 注释规范（JSDoc + 组件注释）

### 3.1 函数注释（JSDoc）

```typescript
/**
 * 解析统一响应体并解包 data。
 * 业务失败（code !== 200）时抛出 Error，由调用方捕获。
 *
 * @param response - 后端 ApiResponse 结构
 * @returns 解包后的业务数据
 * @throws {Error} 当 code !== 200 时抛出，message 为后端返回的错误信息
 */
export function unwrap<T>(response: ApiResponse<T>): T {
  if (response.code !== 200) {
    throw new Error(response.message || '请求失败')
  }
  return response.data as T
}
```

规范要点：
- `@param` 标注参数名与说明，`-` 分隔。
- `@returns` 说明返回值。
- `@throws` 标注抛出条件。
- 类型已由 TypeScript 类型签名表达，注释侧重语义与约束。

### 3.2 Vue 组件注释

```vue
<script setup lang="ts">
/**
 * 通用页面容器。
 * 封装 TopBar、加载态、错误态切换，feature 页面基于此容器组装。
 *
 * @props title - 页面标题
 * @props loading - 是否加载中
 * @props error - 错误信息，非空时显示错误占位
 * @emits retry - 用户点击重试时触发
 * @slot default - 页面内容（加载/错误态时不渲染）
 */
defineProps<{
  title: string
  loading?: boolean
  error?: string
}>()
</script>
```

### 3.3 类型与接口注释

```typescript
/** 后端统一响应体，与 com.forgex.common.web.R 对齐 */
export interface ApiResponse<T> {
  /** 状态码，200 表示成功 */
  code: number
  /** 提示信息 */
  message?: string
  /** 业务数据 */
  data?: T
}
```

### 3.4 Pinia Store 注释

Store 的 state / getter / action 应有注释说明用途，action 遵循函数注释规范。

## 四、Kotlin 注释规范（KDoc）

安卓端 Kotlin 代码使用 KDoc（`/** */`），规范与 Javadoc 类似：

```kotlin
/**
 * 从 DataStore 异步读取当前会话。
 *
 * @return 当前会话，未登录时返回 null
 */
val sessionFlow: Flow<Session?>
```

Compose 组件注释说明 props、slot 与适用场景，参考 Vue 组件注释规范。

## 五、TODO / FIXME 规范

### 5.1 格式

临时占位与已知问题必须用 `TODO` / `FIXME` 标记，并署名 + 日期 + 关联 issue，便于追踪清理：

```
// TODO(zhangsan 2026-06-21 #135): 支持批量导出 Excel，当前仅支持单页导出
// FIXME(lisi 2026-06-20 #142): 高并发下版本号冲突需重试，当前直接抛异常
```

### 5.2 规范

| 项 | 要求 |
|---|---|
| 格式 | `TODO(姓名 日期 issue号): 说明` 或 `FIXME(姓名 日期 issue号): 说明` |
| 署名 | 必填，写责任人姓名或工号，便于追溯 |
| 日期 | 必填，YYYY-MM-DD 格式，标记创建时间 |
| issue | 有则填关联 issue 号，无则写原因 |
| 清理 | TODO 不应长期存在，发布前 review 清理或转为 issue |
| 区别 | `TODO` = 待实现的功能；`FIXME` = 已知缺陷需修复 |

### 5.3 禁止

- 禁止无署名无日期的裸 `TODO`（如 `// TODO: 优化`），无法追踪。
- 禁止用注释掉的大段代码替代删除（交给 Git 历史）。
- 禁止用 `TODO` 掩盖未完成的核心逻辑后提交到 main。

## 六、注释维护要求

1. **改代码必改注释**：PR Review 时检查注释是否同步更新。
2. **过时注释即缺陷**：发现过时注释应在同 PR 修正，不遗留。
3. **注释不替代坏命名**：如果注释在解释变量含义，应重命名变量。
4. **公开 API 文档由注释生成**：后端 Javadoc、前端 JSDoc 是 API 文档的唯一来源，保持准确。
