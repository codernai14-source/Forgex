# 内部服务接口与第三方接口平台说明

> 适用范围：Forgex 体系内服务间接口契约与第三方接入边界

本文用于统一说明两类接口的边界：

- **内部服务接口**：Forgex 各业务模块之间互相调用的接口契约
- **第三方接口平台**：外部系统接入 Forgex 的统一入口，走 `Forgex_Integration`

两者不要混写，也不要混用同一套文档入口。

## 一、内部服务接口怎么定义

### 1.1 存放位置

- 共享 DTO 放在 `com.forgex.common.api.dto`
- Feign Client 放在 `com.forgex.common.api.feign`
- 需要复用的自动填充、鉴权辅助能力，优先放在 `com.forgex.common.api` 下的公共能力目录中

### 1.2 命名原则

- DTO 命名要体现业务对象，例如 `MaterialDTO`、`SupplierAggregateDTO`、`UserInfoDTO`
- Feign Client 命名要体现“谁提供能力、谁被调用”，例如 `SysUserFeignClient`
- 方法命名要直接表达查询动作，例如 `getById`、`listByCodes`、`getUsersByDeptIds`

### 1.3 返回约定

- 内部服务接口优先返回统一包装 `R<T>`
- 单条接口返回对象，批量接口返回集合
- 查询条件复杂时，优先封装请求 DTO，不直接堆一串方法参数

### 1.4 注解约定

- Controller、DTO、Param、VO 都要补齐 `@Tag`、`@Operation`、`@Schema`
- 内部服务契约也要保持接口说明清楚，方便联调和接口文档生成

## 二、内部服务接口和第三方接口平台的区别

### 2.1 内部服务接口

- 服务对象是 Forgex 体系内其他模块
- 调用方式以 Feign、内部 Controller 契约为主
- 重点是稳定、清晰、批量友好
- 不承载第三方系统认证、参数转换、回调编排

### 2.2 第三方接口平台

- 服务对象是 Forgex 体系外部系统
- 统一走 `Forgex_Integration`
- 重点是接入配置、授权、映射、审计、调用日志、结果追踪
- 不要把第三方系统的开放接口直接塞进业务模块内部契约

## 三、推荐的接口开放流程

1. 先确认接口是“模块互调”还是“第三方接入”
2. 如果是模块互调，先在 `common/api` 设计共享 DTO 和 Feign Client
3. 再由对应业务模块实现 Controller 与 Service
4. 接口路径、请求体、返回体保持和契约一致
5. 用 API 文档注解补齐说明，保证其他模块可以直接按文档调用

## 四、调用内部服务接口的建议

- 优先依赖 `com.forgex.common.api.feign` 下的 Client，不自己手写重复 HTTP 调用
- 能批量就批量，减少频繁远程请求
- 调用方只关心契约，不直接依赖提供方内部实现细节
- 需要用户、物料、供应商、客户、部门、职位、角色等主数据时，优先走公共契约，不重复查库

## 五、第三方接入的文档边界

- 第三方系统接入说明继续保留在 `Forgex_Doc/后端/模块专题/集成平台.md`
- 第三方系统的参数映射、签名、回调、调用日志和错误处理，不放进内部服务接口规范
- 如果某个接口既要给内部模块用，又要给外部系统用，应该拆成两套入口，分别归属内部契约和接口平台
