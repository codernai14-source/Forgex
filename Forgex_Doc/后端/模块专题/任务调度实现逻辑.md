# 任务调度实现逻辑

> 分类：后端 / 模块专题
> 版本：**V0.6.5**
> 更新时间：**2026-04-17**

本文档说明 `Forgex_Job` 的调度骨架与扩展边界。

## 当前定位

`Forgex_Job` 是独立任务调度服务，服务端口为 `9004`，数据源使用 `forgex_job`。当前建设方向是 Forgex 自研轻量调度平台，不使用 Snail-Job、XXL-Job、Quartz 等第三方调度框架。

## 路由模型

网关启用 Spring Cloud Gateway discovery locator，模块接口按服务名自动转发：

1. 服务名 `forgex-job` 映射为前端前缀 `/api/job`。
2. 网关将 `/api/job/workflow/page` 重写为 Job 服务内的 `/job/workflow/page`。
3. 业务模块新增接口时不需要逐条修改网关路由；只有新增服务或特殊鉴权豁免时才需要改网关配置。

因此 Job 前端 API 基础路径固定为 `/job`，配合前端 Axios `baseURL: /api` 后，最终请求为 `/api/job/...`。

## 菜单与动态路由

菜单数据由 `Forgex_Doc/数据库/脚本与修复/20260513_init_forgex_job.sql` 初始化：

1. `定时任务` 是 `系统管理` 模块下的一级目录，`path = job`，`component_key = NULL`。
2. Job 各页面作为 `定时任务` 的子菜单，路径分别为 `dashboard`、`task`、`log`、`instance`、`retry`、`alarm`、`alarm-log`、`workflow`。
3. 页面组件保存在前端 `src/views/job`，动态路由 `component_key` 与组件映射保持一致：`JobDashboard`、`JobTask`、`JobLog`、`JobInstance`、`JobRetry`、`JobAlarm`、`JobAlarmLog`、`JobWorkflow`。
4. 如果页面白屏，优先检查数据库动态路由 `component_key` 和前端组件路径，而不是接口返回。

## 技术边界

- 任务定义、执行日志、实例心跳和重试记录以数据库为事实源。
- Cron 下次触发时间优先使用 Spring `CronExpression` 计算，不承诺 Quartz 全部扩展字符。
- 多实例部署通过 Redisson 分布式锁做任务触发互斥。
- 任务执行使用独立线程池，并在执行前恢复租户上下文，执行后清理上下文。
- Java Bean、HTTP、脚本、RocketMQ、DAG、分片/广播任务统一写入任务表和日志表。

## 核心表

| 表名 | 作用 |
|---|---|
| `sys_job_task` | 任务定义，`next_trigger_time` 是调度扫描事实源 |
| `sys_job_log` | 单次触发执行日志 |
| `sys_job_instance` | Job 服务实例心跳与维护模式 |
| `sys_job_retry` | 失败重试和死信 |
| `sys_job_alarm_rule` | 告警规则 |
| `sys_job_alarm_log` | 告警发送日志 |
| `sys_job_workflow*` | DAG 编排、节点、连线和执行历史 |

旧版 `forgex_job.sql` 可能已经创建过 `sys_job`、旧结构 `sys_job_log`。初始化脚本必须可重复执行，并会补齐 `deleted`、`job_code`、`fire_time`、`duration_ms` 等当前实体需要的字段。

## 调度流程

1. `JobScheduleScanner` 按 `forgex.job.scheduler.scan-interval-ms` 扫描启用任务。
2. 扫描条件以 `sys_job_task.next_trigger_time` 为准，只取已到触发时间的任务。
3. 多实例竞争同一触发点时使用 Redisson 锁，锁 Key 形态为 `forgex:job:lock:{tenantId}:{jobId}:{fireTime}`。
4. 获取锁后创建 `sys_job_log`，状态从待执行进入执行中。
5. `JobExecutor` 根据任务类型分发到 Java Bean、HTTP、脚本或 DAG 执行器。
6. 执行成功更新日志、任务上次状态和下次触发时间；执行失败写错误堆栈并按任务重试配置写入 `sys_job_retry`。
7. `JobRetryScanner` 到期扫描重试记录，次数耗尽后进入死信。

## Java Bean 调用边界

`JavaBeanJobInvoker` 只从 `Forgex_Job` 当前 Spring 容器取 Bean：

```java
Object bean = applicationContext.getBean(task.getBeanName());
Method method = bean.getClass().getMethod(methodName, JobExecutionContext.class);
```

这意味着其它微服务的业务 Bean 不能直接填写到 `beanName`。跨模块任务应在 Job 服务内写调度适配 Bean，再通过 Feign 或 HTTP 调用目标模块。

## 安全边界

1. HTTP 任务默认只允许白名单地址，白名单来自 Nacos `job.yml` 的 `forgex.job.security.http-whitelist`。
2. 脚本任务默认关闭，开启后仍必须命中 `script-directory-whitelist`。
3. 脚本输出需要截断记录，避免日志表写入无限输出。
4. 手动触发使用 `requestId` 做防重复，调用方应保证同一业务请求的 `requestId` 稳定。

## 不迁移的任务

以下任务暂不纳入统一调度平台：

- 授权刷新任务，避免授权链路依赖业务调度平台。
- SSE 心跳与连接清理任务，保留在连接服务本地。
- 高频日志刷盘和毫秒级消费扫描任务，优先保留本地线程或 MQ 消费模型。

## 适用任务

- 数据清理和归档。
- 外部系统同步。
- 报表统计。
- 审批或集成任务补偿。
- 制造业场景模板任务。
