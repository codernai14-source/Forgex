# 工作流使用方式

> 分类：后端 / 模块专题
> 版本：**V0.6.6**
> 更新时间：**2026-05-17**

本文档说明工作流模块在项目中的实际使用方式，重点覆盖：

1. 后端如何创建流程、发布流程、发起审批、处理审批。
2. 页面如何配置流程图、发起审批、处理待办。
3. 业务系统如何接解释器、通知和回调。
4. 常见联调与排查步骤。

## 1. 后端代码如何使用

### 1.1 新建一个审批流程

后端创建审批流程通常不是一次性把所有节点都塞进去，而是按“基础信息 -> 草稿流程图 -> 发布”三步走。

常用接口：

- `/wf/task/config/create`
- `/wf/task/config/draft/base/save`
- `/wf/task/config/draft/graph/save`
- `/wf/task/config/draft/publish`

实际推荐顺序：

1. 先创建或获取草稿编辑器
2. 保存草稿基础信息
3. 保存草稿流程图
4. 发布草稿

### 1.2 基础信息怎么配

流程基础信息通常包含：

- `taskName`
- `taskCode`
- `interpreterBean`
- `formType`
- `formPath`
- `status`
- `remark`

建议：

- `taskCode` 保持稳定，不要频繁改
- `interpreterBean` 只有在业务需要挂接解释器时才配置
- `formType` 和前端页面或低代码表单能力保持一致

### 1.3 审批图怎么配

审批图相关接口：

- `/wf/task/config/draft/graph/get`
- `/wf/task/config/draft/graph/save`

配置时至少要确认：

1. 是否有开始节点和结束节点
2. 每个审批节点是否配置了审批人规则
3. 分支节点是否配置了条件
4. 是否允许加签、转交

只把节点拖出来但不配审批人，是最常见的配置错误之一。

审批人建议优先使用稳定来源：

- 指定用户
- 部门
- 角色
- 岗位
- 发起人自选

连续多级上级、部门负责人这类规则暂不建议作为正式流程依赖，因为当前组织模型没有稳定的上级用户 ID 字段，不能只靠部门负责人文本做用户匹配。

### 1.4 发布流程

发布接口：

- `/wf/task/config/draft/publish`

发布后才会生成正式可运行版本。未发布草稿只对配置页面可见，不会在发起审批页中作为正式可用流程出现。

### 1.5 发起审批

发起接口：

- `/wf/execution/start`

后端发起审批时一般需要传：

- `taskCode`
- `formContent`
- 必要时传 `selectedApprovers`

示例思路：

```java
WfExecutionStartParam param = new WfExecutionStartParam();
param.setTaskCode("LEAVE_APPROVAL");
param.setFormContent("{\"days\":3,\"reason\":\"事假\"}");
Long executionId = executionService.startExecution(param);
```

### 1.5.1 业务微服务内部发起（Feign，免用户 Token）

面向 **Forgex_Basic / 其他业务服务**：通常不直接调带 `@RequirePerm` 的 `/wf/execution/start`，而是调用工作流对外暴露的 **内部接口**，由网关或服务发现转发到 `Forgex_Workflow`。

| 说明 | 路径 |
|---|---|
| Feign 客户端 | `Forgex_MOM/Forgex_Backend/Forgex_Common/src/main/java/com/forgex/common/api/feign/WorkflowExecutionFeignClient.java` |
| 请求 DTO | `Forgex_MOM/Forgex_Backend/Forgex_Common/src/main/java/com/forgex/common/api/dto/WorkflowExecutionStartRequestDTO.java` |
| 工作流端映射 | `@PostMapping("/start")` 前缀 `path = "/wf/execution/internal"`（见 Feign 声明） |

```java
import com.forgex.common.api.dto.WorkflowExecutionStartRequestDTO;
import com.forgex.common.api.feign.WorkflowExecutionFeignClient;
import com.forgex.common.web.R;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class DemoStartFromBusiness {

    private final WorkflowExecutionFeignClient workflowExecutionFeignClient;

    /**
     * 从业务服务发起审批。
     *
     * @return executionId
     */
    public Long startDemo() {
        WorkflowExecutionStartRequestDTO request = new WorkflowExecutionStartRequestDTO();
        request.setTaskCode("YOUR_TASK_CODE");
        request.setFormContent("{\"bizId\":1}");
        // request.setSelectedApprovers(List.of(1001L)); // 若首节点为发起人自选则必填
        R<Long> response = workflowExecutionFeignClient.startExecution(request);
        if (response == null || response.getCode() == null || response.getCode() != 200 || response.getData() == null) {
            throw new IllegalStateException("发起审批失败");
        }
        return response.getData();
    }
}
```

### 1.6 审批通过、驳回、转交、加签

常用接口：

- `/wf/execution/approve`
- `/wf/execution/reject`
- `/wf/execution/transfer`
- `/wf/execution/addSign`

这些操作不要自己直接改表状态，必须走统一服务：

- `WfExecutionServiceImpl`

因为它内部还会处理：

- 审批实例更新
- 动作日志
- 通知
- 引擎推进
- 待办生成

### 1.7 批量处理与补偿

工作流还提供了：

- `/wf/execution/batch/approve`
- `/wf/execution/batch/transfer`
- `/wf/execution/batch/remind`
- `/wf/execution/compensate`
- `/wf/execution/timeout/retry`

适用场景：

- 批量审批
- 批量转交
- 批量催办
- 异常恢复
- 超时任务补偿

## 2. 业务系统如何接入工作流

### 2.1 使用解释器

如果业务系统想在审批关键节点执行自己的逻辑，推荐接入解释器，而不是直接改工作流引擎代码。

接入步骤：

1. 实现 `IApprovalInterpreter`
2. 注册为 Spring Bean
3. 在流程配置中填写 `interpreterBean`

适合放在解释器里的逻辑：

- 审批开始时初始化业务状态
- 审批通过后更新业务单据状态
- 审批驳回后回写业务状态
- 审批结束后做收尾动作

不适合放在解释器里的逻辑：

- 替代引擎推进流程
- 修改审批实例底层状态

### 2.2 使用回调

如果业务系统不想直接依赖解释器，也可以使用回调能力。

相关接口：

- 注册：`/wf/callback/register`
- 注销：`/wf/callback/unregister`

适用场景：

- 审批完成后通知外部系统
- 异构服务之间解耦

流程结束时，`WfCallbackServiceImpl` 会向 `callbackUrl` 发起 **HTTP POST**，JSON body 字段为：`executionId`、`taskCode`、`taskName`、`status`、`formContent`（与启动时提交的表单 JSON 一致）。业务侧 DTO 需与之对齐（见下方供应商示例）。

除内存注册外，任务配置表中的 `callbackUrl` / `callbackBean` 也可作为持久化来源（见实现逻辑文档）。

### 2.3 使用通知

通知由工作流统一负责，业务系统一般不需要自行在每个审批动作里再发一遍。

常见通知场景：

- 待办通知
- 审批通过通知
- 审批驳回通知
- 审批完成通知

如果通知内容要业务化，优先通过模板和解释器补数据，不要在页面里拼接通知文本。

### 2.4 完整示例：供应商资质审查（Forgex_Basic）

以下路径与生产代码一致，可作为「业务服务 → 工作流 → 回写业务表」的模板。

#### 2.4.1 任务编码与表单约定

- 任务编码常量：`SUPPLIER_QUALIFICATION_REVIEW`（定义于 `SupplierServiceImpl`）。
- 发起审批前在流程中心维护 **同名** `taskCode` 并已发布、启用。
- `formContent` 为 JSON 字符串，**至少包含** `supplierId`，供回调阶段解析并回写供应商评审状态。

#### 2.4.2 发起审批（Service）

代码位置：`Forgex_MOM/Forgex_Backend/Forgex_Basic/src/main/java/com/forgex/basic/supplier/service/impl/SupplierServiceImpl.java`

核心步骤（与源码一致）：

1. 校验供应商 `reviewStatus` 仅允许从「待审」进入流程。
2. 组装 `WorkflowExecutionStartRequestDTO`：`taskCode`、`formContent`、`selectedApprovers`。
3. 调用 `workflowExecutionFeignClient.startExecution(request)`。
4. 远程成功后将本地供应商状态更新为「审批中」。

表单 JSON 由私有方法 `buildReviewFormContent` 序列化，核心字段示例：

```json
{
  "supplierId": 10001,
  "supplierCode": "S0001",
  "supplierFullName": "示例供应商",
  "qualificationSummary": "资质摘要……",
  "currentReviewStatus": 1
}
```

对应生成逻辑（节选，便于对照字段名）：

```java
private String buildReviewFormContent(BasicSupplier supplier) {
    Map<String, Object> form = new LinkedHashMap<>();
    form.put("supplierId", supplier.getId());
    form.put("supplierCode", supplier.getSupplierCode());
    form.put("supplierFullName", supplier.getSupplierFullName());
    form.put("qualificationSummary", buildQualificationSummary(supplier.getId()));
    form.put("currentReviewStatus", supplier.getReviewStatus());
    return objectMapper.writeValueAsString(form);
}
```

#### 2.4.3 对外接口（Controller）

| 能力 | HTTP | 代码位置 |
|---|---|---|
| 发起审查 | `POST /basic/supplier/review/start` | `SupplierController#startReview`，权限 `basic:supplier:review` |
| 工作流回调 | `POST /basic/supplier/workflow/callback` | `SupplierController#workflowCallback`（**宜配置为工作流回调 URL**，无权限注解以便内网回调） |

回调入参模型：`Forgex_MOM/Forgex_Backend/Forgex_Basic/src/main/java/com/forgex/basic/supplier/domain/param/SupplierWorkflowCallbackParam.java`

```java
@Data
public class SupplierWorkflowCallbackParam {
    private Long executionId;
    private String taskCode;
    private String taskName;
    private Integer status;
    private String formContent;
}
```

#### 2.4.4 回调内业务处理（Service）

`SupplierServiceImpl#handleWorkflowCallback`：

1. 若 `taskCode` 非 `SUPPLIER_QUALIFICATION_REVIEW`，直接返回 `true`（忽略其他流程的误投）。
2. 从 `formContent` 解析 `supplierId`。
3. 若 `status == 2`（与当前工作流「通过」终态约定一致，具体以你们环境字典为准），将评审状态置为「已通过」，否则回退为「待审」类状态。

#### 2.4.5 工作流侧回调注册要点

1. 调用 `/wf/callback/register` 或在任务配置中填写 `callbackUrl`，指向可访问的  
   `{gateway}/basic/supplier/workflow/callback`（或 Basic 服务直连地址，视部署而定）。
2. `taskCode` 必须与 `SUPPLIER_QUALIFICATION_REVIEW` 完全一致。
3. 回调失败仅记日志，不阻断主流程；业务回写应具备幂等或状态机保护。

#### 2.4.6 前端入口（可选阅读）

- 供应商列表与业务操作：`Forgex_MOM/Forgex_Fronted/src/views/basic/supplier/index.vue`（资质审查按钮调用 `POST /basic/supplier/review/start`）。
- 通用工作流发起页：`Forgex_MOM/Forgex_Fronted/src/views/workflow/execution/start.vue`；自定义表单注册：`Forgex_MOM/Forgex_Fronted/src/views/workflow/execution/formRegistry.ts`。

## 3. 页面如何使用

### 3.1 流程配置页面

页面位置：

- `D:\mine_product\forgex\Forgex_MOM\Forgex_Fronted\src\views\workflow\taskConfig\index.vue`

页面用途：

1. 查看流程列表
2. 新建流程草稿
3. 编辑基础信息
4. 进入节点配置页面
5. 发布草稿

页面中已接权限：

- `wf:taskConfig:add`
- `wf:taskConfig:edit`
- `wf:taskConfig:config`
- `wf:taskConfig:delete`

### 3.2 节点配置页面

页面位置：

- `D:\mine_product\forgex\Forgex_MOM\Forgex_Fronted\src\views\workflow\taskConfig\nodes.vue`

页面用途：

1. 配置流程图节点
2. 配置节点规则
3. 配置审批人
4. 保存草稿
5. 发布草稿

联调时重点看：

- 节点是否完整连通
- 分支条件是否正确
- 审批人是否能解析

### 3.3 发起审批页面

页面位置：

- `D:\mine_product\forgex\Forgex_MOM\Forgex_Fronted\src\views\workflow\execution\start.vue`

页面用途：

1. 列出已启用可发起的流程
2. 打开对应表单
3. 提交 `taskCode + formContent`

自定义表单组件统一维护在 `src/views/workflow/execution/formRegistry.ts`。如果业务表单不仅提交工作流表单内容，还需要同步业务单据状态，可以在表单组件中暴露 `startWorkflow` 方法；例如供应商资质审查路径 `/basic/supplier/review` 会优先调用供应商业务发起接口，再进入“我发起的”列表。

这页只会显示可用流程，所以如果流程已经配置但发起页看不到，优先查是否发布和启用。

### 3.4 我的待办、已办、我发起的

页面位置：

- `myTask/pending.vue`
- `myTask/processed.vue`
- `myTask/initiated.vue`

用途分别是：

- 待办处理
- 已处理查询
- 我发起的审批跟踪与撤销

其中待办页已经接了这些按钮权限：

- `wf:execution:approve`
- `wf:execution:reject`
- `wf:execution:transfer`
- `wf:execution:addSign`
- `wf:execution:remind`

发起页中的撤销按钮则依赖：

- `wf:execution:cancel`

## 4. 联调建议

### 4.1 新流程联调顺序

推荐顺序：

1. 创建流程草稿
2. 保存基础信息
3. 配节点和审批人
4. 发布草稿
5. 在发起页确认流程可见
6. 发起一笔审批
7. 在待办页处理
8. 在已办和我发起页查看流转结果

### 4.2 业务集成联调顺序

如果还接了解释器、通知、回调，推荐再补两步：

9. 验证解释器是否按预期触发
10. 验证通知或回调是否发出

## 5. 常见问题排查

### 5.1 流程配置了但发起页看不到

优先检查：

1. 是否已经发布草稿
2. 流程状态是否启用
3. 前端是否调用的是 `listTaskConfig({ status: 1 })`

### 5.2 发起审批成功但没有待办

优先检查：

1. 第一个审批节点是否配置了审批人
2. 审批人规则是否能解析出目标用户
3. 是否误把流程配置成了只草稿未发布版本

如果配置的是上级或部门负责人规则，还需要确认项目是否已经补充稳定的上级/负责人用户 ID 字段；当前默认模型不支持按文本负责人可靠解析。

### 5.3 待办页看不到审批按钮

优先检查：

1. 当前用户是否有对应权限码
2. 当前用户是否真的是该条待办审批人
3. 页面 `v-permission` 是否与后端权限码一致

### 5.4 审批后流程不继续

优先检查：

1. 当前节点后的下一节点是否存在
2. 分支条件是否命中
3. 下一节点审批人是否能解析

### 5.5 加签或转交失败

优先检查：

1. 当前节点规则是否允许加签 / 转交
2. 目标审批人 ID 是否合法
3. 当前审批实例是否仍处于可操作状态

### 5.6 通知没发出来

优先检查：

1. `WorkflowNotificationService` 是否被调用
2. 模板编码是否存在
3. 模板消息失败后是否已降级直发

### 5.7 回调没收到

优先检查：

1. 是否已注册回调
2. `taskCode` 是否一致
3. 回调地址是否可达
4. 审批最终状态是否真的触发了回调时机

### 5.8 补偿中心数据不对

优先检查：

1. 是否确实存在异常执行
2. `compensate` 或 `timeout/retry` 是否已执行
3. 动作处理器是否记录了补偿日志

## 6. 推荐实践

- 工作流定义一定走草稿 -> 发布，不要跳过。
- 每个审批节点都给审批人解析留兜底方案。
- 正式流程优先使用用户、部门、角色、岗位、发起人自选等稳定审批人来源。
- 需要上级或部门负责人审批时，先补组织关系字段，再接入解析逻辑。
- 业务接入优先用解释器或回调，不要直接改引擎。
- 按钮权限、接口权限、待办归属三件事要一起检查，少查一项都容易误判。
