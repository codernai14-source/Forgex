# 集成平台实现逻辑

> 分类：后端 / 模块专题
> 版本：V0.6.5
> 说明：本文说明当前接口平台核心实现逻辑，已覆盖 2026-05 调用日志专项修复内容。

## 1. 总体结构

当前平台围绕 `ApiGatewayServiceImpl` 组织，包含两条主链路：

1. 出站链路：内部服务通过 `IntegrationFacade` 调用第三方接口。
2. 入站链路：外部系统通过 `PublicIntegrationController` 调用内部处理器。

核心参与者：

- `IntegrationFacadeImpl`
- `ApiGatewayServiceImpl`
- `ApiDefinitionServiceImpl`
- `ApiParamAssemblerImpl`
- `ApiOutboundExecutorImpl`
- `ApiLogBufferServiceImpl`
- `ApiCallLogServiceImpl`
- `ApiCallLogTableServiceImpl`

## 2. 配置快照与缓存

运行时不会每次调用都重新拼装多张配置表，而是通过 `ApiDefinitionServiceImpl` 将以下内容编译为 `ApiDefinitionSnapshot`：

- `ApiConfigDTO`
- 请求参数树
- 响应参数树
- 入站映射
- 出站映射
- 出站目标列表

缓存键：

```text
integration:definition:{tenantId}:{direction}:{apiCode}
```

缓存层次：

1. 本地 Caffeine。
2. Redis。

## 3. 参数组装逻辑

参数组装统一由 `ApiParamAssemblerImpl` 负责：

- 入站：`assembleInbound`
- 出站：`assembleOutbound`

支持的规则：

- 路径取值
- 默认值
- 常量值
- 大小写转换
- trim
- number
- boolean
- date:pattern

出站时会组装出完整的 `OutboundRequestDefinition`：

- `body`
- `query`
- `headers`
- `pathVariables`
- `targetUrl`

## 4. 出站执行链路

内部服务调用 `IntegrationFacade.invoke(...)` 后，主流程如下：

```text
IntegrationFacade
  -> ApiGatewayServiceImpl.invokeOutbound
  -> ApiDefinitionServiceImpl.getSnapshot
  -> ApiParamAssemblerImpl.assembleOutbound
  -> ApiOutboundExecutorImpl.execute
  -> ApiGatewayServiceImpl.writeLog
  -> ApiLogBufferServiceImpl.buffer
```

如果配置了多个出站目标：

- 每个目标独立组装参数。
- 每个目标独立执行。
- 每个目标独立记录日志。

## 5. 入站执行链路

外部系统调用 `POST /api/integration/public/invoke` 后，主流程如下：

```text
PublicIntegrationController
  -> ApiGatewayServiceImpl.invokeInbound
  -> ApiDefinitionServiceImpl.getSnapshot
  -> token 校验
  -> ApiParamAssemblerImpl.assembleInbound
  -> ApiInterpreterRegistry.get(processorBean)
  -> 同步执行或提交异步任务
  -> ApiGatewayServiceImpl.writeLog
  -> ApiLogBufferServiceImpl.buffer
```

即使鉴权失败，平台也会记录失败日志，便于排查。

## 6. 异步任务模型

异步接口使用：

- 任务表 `fx_api_task`
- 结果表 `fx_api_task_result`
- Redis 队列
- 定时消费与补偿

基本过程：

1. 写任务表。
2. 推入 Redis 队列。
3. 消费线程执行任务。
4. 成功后写结果表并清理任务表。
5. 失败则按重试策略处理。

## 7. 调用日志月表维护

调用日志按月分表，表名固定为：

- `fx_api_call_log_yyyyMM`

本次修复后的生命周期：

1. 服务启动后自动确保当月表和下月表存在。
2. 每天定时检查当月表。
3. 月末提前创建下月表。
4. 每次写日志前按 `callTime` 再次兜底建表。
5. 查询时先过滤实际存在的月份表。

这样解决了两个问题：

- 新月份未提前建表导致插入失败。
- 历史月份缺表导致查询直接报错。

## 8. 调用日志写入策略

日志对象由 `ApiGatewayServiceImpl.writeLog(...)` 构建，写入内容包括：

- `raw_request_data`
- `request_data`
- `assembled_request_data`
- `response_data`
- `response_code`
- `call_status`
- `result_type`
- `error_message`
- `cost_time_ms`
- `trace_id`
- `task_id`
- `outbound_target_id`
- `target_system_code`
- `target_system_name`

日志先进入 `ApiLogBufferServiceImpl` 的内存队列，再由定时刷新批量落库。

为保证日志不会因为同类自调用导致异步失效，批量刷新路径已改为直接同步入库。

## 9. 查询兜底策略

调用日志分页、列表、次数统计、成功率统计都采用相同策略：

1. 根据时间范围推导候选月份表。
2. 过滤不存在的月份表。
3. 仅对存在的月份表执行动态 SQL。

因此单个月份表缺失时：

- 不会抛 `Table ... doesn't exist`
- 会跳过该月并记录告警日志

## 10. 初始化脚本修正

部署脚本 `forgex_integration.sql` 已追加修正版日志表 DDL：

1. 修正 `fx_api_call_log_202604` 字段不完整问题。
2. 补齐 `fx_api_call_log_202605`，方便当前环境直接执行。

当前日志表结构以代码中的 `ApiCallLog` 与 `ApiCallLogMapper.xml` 为准。
