# 集成平台实现逻辑

> 分类：后端 / 模块专题
> 版本：V0.6.5
> 说明：本文说明当前接口平台核心实现逻辑，已覆盖 2026-05 调用日志专项修复内容。

## 1. 总体结构

当前平台围绕 `ApiGatewayServiceImpl` 组织，包含两条主链路：

1. 出站链路：内部服务通过 `IntegrationFacade` 调用第三方接口。
2. 入站链路：外部系统通过 `PublicIntegrationController` 调用内部处理器。

核心参与者：

- `IntegrationFacadeImpl`
- `ApiGatewayServiceImpl`
- `ApiDefinitionServiceImpl`
- `ApiParamAssemblerImpl`
- `ApiOutboundExecutorImpl`
- `ApiLogBufferServiceImpl`
- `ApiCallLogServiceImpl`
- `ApiCallLogTableServiceImpl`

## 2. 配置快照与缓存

运行时不会每次调用都重新拼装多张配置表，而是通过 `ApiDefinitionServiceImpl` 将以下内容编译为 `ApiDefinitionSnapshot`：

- `ApiConfigDTO`
- 请求参数树
- 响应参数树
- 入站映射
- 出站映射
- 出站目标列表

缓存键：

```text
integration:definition:{tenantId}:{direction}:{apiCode}
```

缓存层次：

1. 本地 Caffeine。
2. Redis。

## 3. 参数组装逻辑

参数组装统一由 `ApiParamAssemblerImpl` 负责：

- 入站：`assembleInbound`
- 出站：`assembleOutbound`
- 出站响应回写：`assembleOutboundResponse`

支持的规则：

- 路径取值
- 默认值
- 常量值
- 大小写转换
- trim
- number
- boolean
- date:pattern

出站时会组装出完整的 `OutboundRequestDefinition`：

- `body`
- `query`
- `headers`
- `pathVariables`
- `targetUrl`

字段级映射要求：

- 映射关系以字段路径为准，不依赖双方字段同名。
- 路径中的 `root` 是参数树根节点，运行时组装 JSON 时不会作为真实字段输出。
- 数组对象必须配置到叶子字段，例如 `root.users.account -> root.commonUsers.code`。
- 当来源路径中某一段是数组时，组装器会按数组下标遍历并合并同一目标数组对象，形成第三方要求的集合结构。
- 如果没有配置字段级映射，平台不会证明“参数转换正确”，只代表接口路由可能被调用到了。
- `ApiParamMappingServiceImpl` 保存 `BODY` 映射时会校验来源路径和目标路径是否存在于当前接口、当前出站目标的请求树或响应树，避免落库悬空字段。
- 出站接口参数配置弹窗会同时读取请求树和响应树；对 `sys_user_pull` 这类“外调请求 + 外部响应回写”的接口，`OUTBOUND` 和 `INBOUND` 两段映射都可以从双方树中选择字段并显示类型。

## 4. 出站执行链路

内部服务调用 `IntegrationFacade.invoke(...)` 后，主流程如下：

```text
IntegrationFacade
  -> ApiGatewayServiceImpl.invokeOutbound
  -> ApiDefinitionServiceImpl.getSnapshot
  -> ApiParamAssemblerImpl.assembleOutbound
  -> ApiOutboundExecutorImpl.execute
  -> ApiParamAssemblerImpl.assembleOutboundResponse
  -> ApiGatewayServiceImpl.writeLog
  -> ApiLogBufferServiceImpl.buffer
```

如果配置了多个出站目标：

- 每个目标独立组装参数。
- 每个目标独立执行。
- 如果当前目标配置了 `INBOUND` 响应映射，第三方响应会先从标准响应包 `data` 中取出，再映射回内部结构。
- 每个目标独立记录日志。

以用户拉取第三方为例，链路中存在两次参数转换：

1. `OUTBOUND` 映射把 Forgex 拉取条件组装为第三方请求体，例如 `tenantId/includeDisabled` 转成 `companyId/includeStop`。
2. 第三方返回后，`INBOUND` 映射把 `commonUsers.code/name/mail` 等字段转换回 Forgex `users.account/username/email`。

这两段不能用整包数组透传代替，否则第三方字段名与 Forgex 字段名不一致时无法验证接口平台的转换能力。

## 5. 入站执行链路

外部系统调用 `POST /api/integration/public/invoke` 后，主流程如下：

```text
PublicIntegrationController
  -> ApiGatewayServiceImpl.invokeInbound
  -> ApiDefinitionServiceImpl.getSnapshot
  -> token 校验
  -> ApiParamAssemblerImpl.assembleInbound
  -> ApiInterpreterRegistry.get(processorBean)
  -> 同步执行或提交异步任务
  -> ApiGatewayServiceImpl.writeLog
  -> ApiLogBufferServiceImpl.buffer
```

即使鉴权失败，平台也会记录失败日志，便于排查。

## 6. 异步任务模型

异步接口使用：

- 任务表 `fx_api_task`
- 结果表 `fx_api_task_result`
- Redis 队列
- 定时消费与补偿

基本过程：

1. 写任务表。
2. 推入 Redis 队列。
3. 消费线程执行任务。
4. 成功后写结果表并清理任务表。
5. 失败则按重试策略处理。

## 7. 调用日志月表维护

调用日志按月分表，表名固定为：

- `fx_api_call_log_yyyyMM`

本次修复后的生命周期：

1. 服务启动后自动确保当月表和下月表存在。
2. 每天定时检查当月表。
3. 月末提前创建下月表。
4. 每次写日志前按 `callTime` 再次兜底建表。
5. 查询时先过滤实际存在的月份表。

这样解决了两个问题：

- 新月份未提前建表导致插入失败。
- 历史月份缺表导致查询直接报错。

## 8. 调用日志写入策略

日志对象由 `ApiGatewayServiceImpl.writeLog(...)` 构建，写入内容包括：

- `raw_request_data`
- `request_data`
- `assembled_request_data`
- `response_data`
- `response_code`
- `call_status`
- `result_type`
- `error_message`
- `cost_time_ms`
- `trace_id`
- `task_id`
- `outbound_target_id`
- `target_system_code`
- `target_system_name`

日志先进入 `ApiLogBufferServiceImpl` 的内存队列，再由定时刷新批量落库。

为保证日志不会因为同类自调用导致异步失效，批量刷新路径已改为直接同步入库。

## 9. 查询兜底策略

调用日志分页、列表、次数统计、成功率统计都采用相同策略：

1. 根据时间范围推导候选月份表。
2. 过滤不存在的月份表。
3. 仅对存在的月份表执行动态 SQL。

因此单个月份表缺失时：

- 不会抛 `Table ... doesn't exist`
- 会跳过该月并记录告警日志

## 12. 入站授权实现补充说明

外部系统调用 `POST /api/integration/public/invoke` 后，`ApiGatewayServiceImpl.invokeInbound` 会先读取接口配置快照，再执行入站授权校验。

校验规则如下：

- 如果接口配置 `auth_type` 为空或 `NONE`，不做第三方授权校验。
- 平台优先从请求体 `thirdSystemId` / `third_system_id` 读取第三方系统 ID；没有时读取 `fx_api_config.auth_config.thirdSystemId`。
- 如果配置了第三方系统 ID，并且调用方 IP 命中该系统 `WHITELIST` 或 `TOKEN_WHITELIST` 白名单，直接放行。
- 如果没有配置第三方系统 ID，但调用方 IP 命中任意启用的白名单授权，也直接放行。
- 未命中白名单时，平台从请求体 `token`、`authToken` 或 `authorization.token` 读取 Token，并校验 Token 是否存在、启用、未过期。
- Token 过期时间为空表示无期限；按天、月、年、指定时间生成的 Token 会落到 `token_expire_type`、`token_expire_value`、`token_expire_time`。

## 13. 错误返回与国际化解析逻辑

接口平台错误返回统一通过 `IntegrationPromptEnum` 和 `fx_i18n_message` 解析，不再依赖硬编码中文或底层异常原文。

核心链路：

1. 业务层抛出 `I18nBusinessException`，携带 `IntegrationPromptEnum` 和占位符参数。
2. `GlobalExceptionHandler` 转换为 `R.failWithArgs(...)`，保留国际化元信息。
3. `RMessageI18nAdvice` 在响应写出前读取 `R.messageCode` / `R.i18n`，调用 `I18nMessageService` 解析最终文案。
4. `I18nMessageServiceImpl` 优先从 `forgex_common.fx_i18n_message` 读取 `module + prompt_code`，按当前语言返回文案；数据库不可用时才回退枚举默认模板。

集成网关专项处理：

- 入站授权失败时，`ApiGatewayServiceImpl.invokeInbound` 会写入失败日志并抛出 `API_AUTH_FAILED`，接口响应和调用日志保持同一份国际化文案。
- 入站处理器执行失败时，未知异常统一包成 `API_INBOUND_EXECUTE_FAILED`，避免直接返回线程池、反射或空指针等底层异常。
- 出站调用失败时，`IntegrationTargetResult.errorMessage` 使用解析后的国际化文案，多个目标时每个目标独立记录错误。
- 目标路由配置错误、第三方系统地址缺失、出站目标缺失分别返回 `API_TARGET_ROUTE_ONLY_PATH`、`API_THIRD_SYSTEM_IP_REQUIRED`、`API_OUTBOUND_TARGET_REQUIRED`，不再统一显示抽象的“路由处理器失败”。

运行时依赖：

- `Forgex_Integration` 的动态数据源配置必须包含 `integration` 和 `common`。
- `common` 指向 `forgex_common`，用于读取 `fx_i18n_message`。
- 提示码初始化脚本为 `Forgex_Doc/数据库/脚本与修复/20260511_integration_i18n_error_messages.sql`。
