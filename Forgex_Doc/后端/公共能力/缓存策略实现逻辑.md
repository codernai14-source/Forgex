# 缓存策略实现逻辑

> 版本：**V1.0.0**

## 源码位置与流程

- Redis 工具：Forgex_MOM/Forgex_Backend/Forgex_Common_Infra/src/main/java/com/forgex/common/util/RedisHelper.java
- 字典缓存：Forgex_Common_Infra/src/main/java/com/forgex/common/dict/DictI18nResolver.java、config/DictCacheConfig.java
- 业务读写流程：写数据库成功 -> 清理 Redis/本地缓存 -> 发布失效消息 -> 下次读取回源并重建

新增缓存前应先确认真实数据源、租户维度、TTL、失效入口和异常回退；当前 RedisHelper 和字典缓存是已实现能力，其他模块是否接入必须以对应源码为准。

Forgex 当前缓存能力主要由 `RedisHelper`、Spring Data Redis、Caffeine 和字典缓存配置组成。缓存策略文档用于约束横向缓存设计，不替代具体业务模块文档。

## 一、RedisHelper

`com.forgex.common.util.RedisHelper` 封装常用 Redis 操作，提供字符串、JSON、删除、存在性判断和锁等能力。业务服务应优先使用该工具，避免在各模块重复封装 RedisTemplate 细节。

## 二、字典三级缓存

字典相关能力使用 Caffeine + Redis + 数据库的三级结构：

1. L1 本地缓存：Caffeine，适合高频读取，降低 Redis 压力。
2. L2 Redis：跨实例共享，作为分布式缓存层。
3. L3 数据库：最终数据源。

`DictCacheConfig` 配置本地缓存和 Redis 监听容器；`DictCacheInvalidationListener` 接收失效消息后清理本地 Caffeine 缓存，保证多实例最终一致。

## 三、失效链路

缓存失效应遵循以下顺序：

1. 业务数据写库成功。
2. 删除或更新 Redis 缓存。
3. 发布缓存失效消息或调用本地清理方法。
4. 下次查询从数据库回源并重新写入缓存。

如果业务更新涉及多个 key，应集中封装失效方法，避免遗漏。

## 四、并发与一致性

- 缓存是性能优化层，不作为强一致事务边界。
- 强一致场景以数据库事务结果为准。
- 热点回源时可使用 Redis 锁保护，避免多个实例同时打到数据库。
- 本地缓存 TTL 应短于或等于业务可接受的不一致窗口。

## 五、扩展新缓存的检查点

- 是否有明确 key 命名和租户维度。
- 是否有 TTL 或主动失效机制。
- 是否有数据库回源和异常兜底。
- 是否会缓存敏感数据。
- 是否需要跨实例失效通知。
