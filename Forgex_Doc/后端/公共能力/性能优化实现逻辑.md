# 性能优化实现逻辑

> 版本：**V0.8.5**

Forgex 性能优化依赖分层治理：前端减少无效渲染和大响应，网关保持转发链路清晰，后端控制查询和事务边界，数据库通过索引和执行计划保障稳定性。

## 一、分页与查询

标准管理页面应采用分页接口。Service 层使用 MyBatis-Plus 或 MPJ 构造查询条件，Mapper 只承载必要的数据访问逻辑。复杂 SQL 应放在 XML 中，避免注解 SQL。

分页接口需要稳定排序，常见排序字段包括 `create_time`、`update_time`、业务编码等。没有排序的分页在数据变化时容易出现重复或遗漏。

## 二、索引配合

接口新增查询条件时，应同步检查表结构：

- 等值过滤字段适合普通索引或联合索引前缀。
- 租户隔离表常见查询应考虑 `tenant_id` 与业务字段组合。
- 逻辑删除字段通常与业务查询条件一起出现。
- 排序字段如果参与高频分页，应结合 WHERE 条件评估联合索引。

## 三、批量处理

批量新增、批量删除、导入导出等场景应避免逐条远程调用或逐条查询。可按业务边界采用批量查询、批量保存、分批提交和异步任务。

## 四、缓存层

缓存层用于降低热点读取压力。字典能力已经具备 Caffeine + Redis + 数据库结构；其他业务缓存应参照缓存策略文档，明确 key、TTL、失效和租户维度。

## 五、观测与日志

性能问题定位依赖以下信息：

- 网关与服务访问日志。
- 业务关键节点耗时日志。
- 数据库慢查询日志。
- JVM 与进程资源使用情况。
- 前端接口耗时和资源加载情况。

生产环境不应通过大量 debug 日志定位性能问题；需要临时加日志时，应控制范围并在问题解决后清理。
