# 缓存策略使用方式

> 版本：**V0.8.5**

Forgex 后端缓存优先使用项目已有能力：简单键值和分布式场景使用 `RedisHelper`，高频读取且允许短暂延迟的本地热点数据使用 Caffeine，跨实例一致性通过 Redis 消息或显式失效处理。

## 一、适用场景

| 场景 | 推荐方式 |
|---|---|
| 验证码、登录临时状态 | Redis，设置较短 TTL |
| 字典、多语言标签等高频读数据 | Caffeine + Redis + 数据库 |
| 编码规则、系统配置 | Redis 或业务服务封装缓存 |
| 分布式互斥 | `RedisHelper` 分布式锁能力 |
| 大对象、强一致交易数据 | 谨慎缓存，优先查询数据库或做专用设计 |

## 二、Key 命名

缓存 key 应具备模块、业务、租户和主键维度，推荐格式：

```text
forgex:{module}:{scene}:{tenantId}:{businessKey}
```

示例：

```text
forgex:sys:dict:1001:material_type
forgex:auth:captcha:slider:{token}
forgex:basic:material:1001:{materialId}
```

## 三、TTL 建议

| 数据类型 | TTL 建议 |
|---|---|
| 验证码、一次性 token | 秒级到分钟级 |
| 登录态辅助信息 | 与 token 生命周期匹配 |
| 字典、配置、枚举 | 分钟级或按变更主动失效 |
| 查询结果缓存 | 根据业务变化频率设置，避免长期缓存 |

不允许无边界缓存租户业务数据；确需长期缓存时必须有明确失效入口。

## 四、使用约定

- 读取缓存失败时应能回源数据库或服务，不影响主流程可用性。
- 写入数据库成功后再失效相关缓存。
- 删除、禁用、状态变更等操作必须同步处理缓存失效。
- 多租户数据必须带租户维度，公共数据可使用 `0` 或明确公共 key。
- 缓存内容不要保存明文敏感信息，日志中不要输出完整缓存值。

## 五、常见风险

- 缓存穿透：对不存在的数据设置短 TTL 空值或在查询入口限流。
- 缓存击穿：热点 key 回源时使用互斥锁或短时间本地缓存。
- 缓存雪崩：批量 key 设置 TTL 时加入随机抖动。
- 脏数据：更新成功后未失效缓存，或只失效本实例本地缓存。
